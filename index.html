Case Studies

Three production systems where the architectural decisions had measurable business consequences. Each shows the real constraint, the tradeoff made, and the outcome.

IPCOM Telecomunicaciones — CPaaS Messaging Platform
Lead Backend Engineer Nov 2024 – May 2025
▲

Problem

IPCOM's CPaaS platform needed to handle real-time voice, WhatsApp, RCS, and OTP delivery at 1M+ messages/day across integrations with Google, Meta, ConceptoMovil, and Telcel. The legacy SIP stack had a ceiling on concurrent sessions that the product was hitting at peak — every provider integration was a custom point-to-point connection with no shared reliability layer.

Constraints

Real-time latency: voice and messaging flows have hard sub-second requirements — batch processing or polling was not acceptable. Multi-provider coupling: Google, Meta, and Telcel each have different auth schemes, rate limits, and message formats. A single abstraction layer had to normalize them without leaking provider-specific logic into business code. Session stability: the SIP → PJSIP migration had to happen without dropping active calls.

Solution

Built Go microservices with worker pools for inbound message distribution. Introduced NATS for asynchronous internal routing between provider adapters, decoupling ingestion from delivery. Redis rulesets replaced synchronous DB lookups on the hot path, cutting per-message DB load. Migrated streaming from SIP to PJSIP incrementally using a session bridge, allowing concurrent traffic on both stacks during cutover. ASR/TTS pipelines were cached at the Redis layer to avoid repeated external API calls per session.

Throughput 1M+ msg/day sustained production traffic across all channels
Session stability +50% concurrent sessions post SIP → PJSIP migration
DB load (hot path) −40% Redis ruleset cache eliminated synchronous reads
BYONDIT / Millicom — Tigo Money Digital Wallet
Backend Engineer Nov 2022 – Aug 2023
▼

Problem

Tigo Money Guatemala operated on a mix of legacy SOAP/REST services for core wallet operations. Third-party integrations (bank transfers, merchant payments, mobile top-ups) were each direct connections with no shared gateway — adding a new integration took weeks of bespoke work. There was no distributed tracing, so incident investigation meant reading logs across isolated services with no correlation.

Constraints

Financial compliance: all transaction flows required end-to-end auditability. Secrets for Oracle SQL, DynamoDB, and external payment APIs were scattered in config files — hardening was mandatory before any feature work. Legacy parity: the KrakenD gateway layer had to proxy existing SOAP/REST contracts without changes to downstream consumers while new Go services replaced backend logic incrementally.

Solution

Built custom Go plugins for KrakenD that normalized SOAP/REST responses behind a unified API surface — downstream clients saw no change while the backend was replaced. Migrated secret management to AWS Secrets Manager and Parameter Store, eliminating plaintext credentials. Added OpenTelemetry instrumentation across all services, giving the team trace-level visibility into every transaction path for the first time. Serverless compute (AWS Lambda) handled low-frequency but latency-sensitive flows like fraud checks, isolating them from the main transaction path.

Stack

Go Python (FastAPI) KrakenD AWS Lambda DynamoDB Oracle SQL AWS Secrets Manager OpenTelemetry Grafana
Integration time −30% new third-party integrations via KrakenD plugin model
MTTR −35% distributed tracing via OpenTelemetry across all services
Independent Consulting — CI/CD Pipeline Modernization
Senior Backend Consultant 2021 – Present · Multiple clients
▼

Problem

Multiple clients running distributed Go service backends had CI pipelines with 6-hour runtimes. The root cause was the same across projects: undifferentiated pipelines that ran full test suites and container builds for every service on every commit, regardless of what changed. Engineers were batching PRs, running tests locally, and in some cases bypassing CI entirely — the pipeline had become decorative.

Constraints

No new infrastructure budget: solutions had to work within existing GitHub Actions runner quotas — adding more hardware was not available as a lever. Shared libraries: genuine cross-service dependencies meant some full-rebuild scenarios were legitimate and had to be distinguished from phantom dependency rebuilds. No big-bang rewrite: pipelines had to migrate incrementally without blocking ongoing releases.

Solution

Implemented dependency graph analysis at the pipeline level to trigger only affected service builds per commit. Introduced remote artifact caching so unchanged layers were never rebuilt across pipeline runs. Parallelized independent service pipelines that had been running sequentially. The architectural tradeoff was accepting more complex pipeline configuration — a one-time cost — in exchange for build time that scales with change scope, not repository size. Also migrated legacy SOAP/XML service contracts to gRPC + REST in Go, reducing cloud platform costs 20–25% per client via right-sized K8s workloads and Terraform-managed reserved capacity.

Stack

GitHub Actions Go Docker Kubernetes Terraform GCP AWS gRPC
Build time 6 h → 20 min −94%, same GitHub Actions quota, no new infra
Cloud costs −20 to −25% per client, K8s + Terraform right-sizing
Production uptime 99.5% across production microservices, multiple clients

How I Think

Three engineering positions I hold and have applied in production. Not principles from a book — observations from breaking things and fixing them.

// On distributed systems

The most consistent mistake I see is teams distributing systems before they've proven the domain boundary is stable. A microservice architecture doesn't reduce complexity — it moves it from the code into the network and the deployment pipeline. If the team can't draw the service boundary on a whiteboard without arguing for 20 minutes, the boundary isn't ready to be a service boundary.

At IPCOM, the right move was building Go worker pools with internal NATS routing before any external service boundary — the traffic volume justified distribution, but the domain had been running long enough that the message types were stable. At Tigo Money, we used KrakenD as a seam: the old boundaries stayed intact externally while we replaced internals. That's the pattern I default to — strangle from a stable interface, never rewrite the interface mid-migration.

// On cloud costs

Cloud bills are a read of the architecture. Idle compute means synchronous coupling somewhere upstream — something is holding a thread waiting for something else. Storage costs growing faster than data volume usually means no retention contract was ever defined. Unpredictable egress costs almost always mean a service is materializing more data than it needs for a query.

My default approach: instrument first, cut second. I've seen teams delete "unused" resources that turned out to be critical to a secondary system with no monitoring. The 25% cost reductions I've achieved came from Terraform audits of provisioned vs. actual usage, right-sizing K8s resource requests to real p95 consumption, and moving predictable workloads to committed use. None of it required changing application code. The architecture already contained the savings — they just weren't visible without the right tooling.

// On CI/CD

A pipeline that takes longer than 10 minutes will be bypassed. Not by lazy engineers — by rational ones. If the feedback loop costs more time than the confidence it buys, people stop using it. That's not a discipline problem. That's a pipeline design problem.

The specific technique most teams skip: scaling build time with change scope instead of repository size. Running the full test suite on every commit in a 30-service repo is a choice, not a requirement. Dependency graph analysis at the CI layer is not exotic — it's available in most modern build tools and in GitHub Actions with minimal configuration. The resistance I encounter is usually not technical; it's that someone has to own the pipeline the way a product team owns a product. That ownership gap is where the 6-hour builds live.
