transaction-event-processor active · Go
The problem: idempotency under concurrent load. When multiple workers race to process the same event, you get duplicate writes, dirty state, and cascading failures downstream. The question is how to prevent that without serializing everything and killing throughput.
Architecture:non-blocking ingestion — HTTP returns 202 immediately, events processed asynchronously through a configurable goroutine worker pool.
Idempotency:Redis SetNX as the distributed lock — atomic, TTL-bounded, no duplicate processing across replicas.
Resilience:gobreaker circuit breaker on PostgreSQL — prevents cascading failures when the DB degrades under write pressure.
Go · Echo · PostgreSQL · Redis · gobreaker github.com/jjvnz/transaction-event-processor →
AI orchestration layer production · Go + FastAPI
LLM outputs are non-deterministic. Integrating them into backend workflows without strict output contracts produces brittle systems: the model changes a field name, the downstream parser breaks, the pipeline silently corrupts data. The problem isn't the model — it's the missing boundary between probabilistic generation and deterministic processing.
Contract layer:JSON Schema output contracts enforced at the LLM boundary — the model is prompted to produce structured output, validated against schema before any downstream processing.
Runtime:Go orchestrator managing agent lifecycles and retry logic, FastAPI handling the model-facing interface.
Infra:Kubernetes + Terraform + GitHub Actions — same deployment discipline as core banking services, not a Colab notebook.
Go · FastAPI · Kubernetes · Terraform · GitHub Actions · LLM APIs production client work · architecture on request
order-system active · Clojure
Not a portfolio checkbox. A working question: what does concurrent state management look like when immutability is structural rather than enforced by convention? Built to understand what Go's concurrency model leaves out — and to make that understanding precise enough to be useful back in Go.
Model:event-driven order processing using Clojure's STM — coordinated state transitions without locks, without the race conditions that locks introduce.
Architecture:Clean Architecture + DDD in a functional paradigm — domain logic stays pure, side effects are pushed to the boundary.
Outcome:concrete vocabulary for discussing state, concurrency, and failure modes across different runtime models.
